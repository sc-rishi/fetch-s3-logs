# babel-order-model

sc-integrations-babel — the Order model, its enums, indexes and save state machine.

**branch when read:** sc-integrations-babel=production (d3dd6cd, v6.3.2) | sc-babel=stableApi/production (8e9e6d2, v18.2.0 installed) | sc-platform-babel=production (4ce58d4) | sc-integrations-jobs=production | sc-integrations-order-updates=production | sc-smallboard-be=production | sc-platform-api=production | sc-integrations-broker-lib=development | sc-integrations-leprechaun=rebalance-in-amo | sc-integrations-broker-api=production

The `orders` collection holds one document per BATCH (not per stock). Its canonical schema for SBI/SBI-MTF is `sc-integrations-babel/src/models/_schema.js` + `src/models/Order.js` (v6.3.2), but TWO other packages define models over the SAME `orders` collection with different, older field sets and different status enums: `sc-platform-babel` (used by sc-platform-api, and by several sc-integrations-jobs scripts) and `sc-babel` v18.x (used by sc-smallboard-be, platform-jobs). Each babel ships its own nested mongoose 6.13.8, so they are separate model registries and separate connection pools — a single job can hold both open at once. The document has exactly one audit trail (`meta.updates[]`, an append-only `{date, update}` array) and exactly one writer-identity field (`meta.source`), plus weaker provenance signals (`dummy`/`meta.dummySource`, `dealer`, `meta.type`, `orders[].meta.reconciled`, `orders[].statusMessage`). Writes reach the collection three ways: through the `Order.saveOrder` mongoose static (4 states: INITIAL/PLACED/FINAL/AUTO), through direct `Order.updateOne`/`bulkWrite` calls in ~20 jobs and services (some of which push their own identity-bearing `meta.updates` string, some of which are completely silent), and through the raw driver `db.collection('orders').insertOne()` in two SBI recon helpers — which bypasses mongoose schema validation entirely and is how undeclared fields like `meta.type` get into prod documents. The single most important correction for an investigator: the batch-level terminal value is `COMPLETED` and the leg-level terminal value is `COMPLETE` — they are two different enums, both real, and neither is a typo.

Confidence markers are the researcher's own: unmarked = confirmed from source, `[INFERRED]` = deduced but unproven, `[UNCONFIRMED]` = a lead, not a fact. `!` marks facts flagged critical. Re-verify line numbers against the checked-out SHA.

### status-enum

- **!** SETTLED: Order.status (batch level) and orders[].status (leg level) are TWO DIFFERENT ENUMS. ### calctxnfields

- **!** calcTxnFields(order, sst=false) recomputes buyAmount/sellAmount from sum(averagePrice*filledQuantity) per leg by transactionType, then DERIVES batch status: filled>0 && quantity==filled -> COMPLETED; filled>0 && quantity>filled -> PARTIALLYFILLED (or MARKEDCOMPLETE if sst); filled==0 && (buyAmount||sellAmount) -> PARTIALLYFILLED; filled==0 && variety=='amo' && every leg 'CANCELLED AMO' -> CANCELLED; filled==0 && unplaced.length==quantity -> 'UNPLACED' (hardcoded literal, not the constant); else UNFILLED. **Claimed:** §3 'orders.tag/unplaced.tag/.orderId are unindexed array fields, so an unbounded query is a full collection scan' — presented as an absolute reason to refuse tag/orderId queries without a date bound.

**Actually:** The unindexed claim is correct, but the conclusion is over-broad. A tag query IS cheap when it is prefixed by an indexed field. The {broker:1, brokeruserId:1} compound index makes {broker:{$in:['sbi','sbi-mtf']}, brokeruserId, $or:[{'orders.tag':tag},{'unplaced.tag':tag}]} index-supported — this is exactly the pattern the SBI rejected-AMO ingest job uses in prod. **Claimed:** Implicit throughout the guide: that `Order.quantity` and `Order.filled` are share counts, and that a batch is 'one order'.
